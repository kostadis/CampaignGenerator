# Party Roster — Canonical Format, 2026-08-10

## Why this doc exists

`session_doc/roster.py` reconstructs `{name, player, species, class, level,
subclass}` from **six** hand-authored `party.md` layouts, and returns them
re-flattened into a string for prompt injection. Its `_parse_class_line` alone
is 77 lines at complexity 11. `extract_character_roster` has 22 in-graph callers
and feeds every narration run.

The obvious reading is "the parser needs a seventh branch" — that is what #248
proposes. This document argues the opposite, on evidence, and records the GM
ruling that settles it.

Companion: **`docs/design/MarkdownAsInput.md`**, which places this finding among
four others sharing a cause.

---

## GM ruling

> **The D&D Beyond character sheet is canonical for all character-specific
> data.**

`party.yaml` references the sheet. It does not restate it. A level-up edits one
file.

This supersedes an earlier draft of this design, which proposed adding
`species` / `class_level` fields to `PartyCharacter`. That draft was wrong: it
would have created a second hand-maintained copy of data D&D Beyond already owns.

---

## Three verified facts

### 1. The sheets already share one format

Two campaigns, independently authored, byte-comparable structure:

```
# Zalthir                                  # Soma
                                           
## Identity                                ## Identity
- **Class & Level:** Monk 8                - **Class & Level:** Druid 6
- **Species:** Dragonborn (Brass Dragon)   - **Species:** Tortle
- **Background:** Sailor                   - **Background:** Guide
- **Player:** Gabe                         - **Player:** Wade
- **Alignment:** Neutral Good              - **Alignment:** Neutral
```

(`out-of-the-abyss/docs/zalthir.md:1–8`, `Phandalin/docs/party/soma.md:1–8`)

One format — because one prompt produced them:
`pipelines/content_ingest/dnd_sheet.py`'s `SYSTEM_PROMPT` specifies exactly this
`## Identity` block.

**The six dialects exist only in `party.md`, the derived document.** The
canonical source was never ambiguous. The parser is reconstructing, from six
prose renderings, fields that are sitting in one consistent shape one directory
over.

### 2. A live factual conflict — and the code reads the wrong side

| Source | OOTA Zalthir, species |
|---|---|
| `docs/zalthir.md:5` — D&D Beyond sheet | `Dragonborn (Brass Dragon)` |
| `docs/party.md:24` — generated by `party.py` | `Bronze Dragonborn` |

`roster.py` reads `party.md`. Verified by running it:

```
- Zalthir (Gabe): Bronze Dragonborn Monk 8 (Warrior of Shadow)
```

Every `sd_narrate` run in that campaign is currently injecting the wrong dragon
colour into the "Character Classes (definitive — never contradict these)" block.

This is not a new rule. `CLAUDE.md` already states it, under provenance:

> *A `generated_by` hit is a draft with a countdown on it … when a render
> pipeline needs a fact and an authoritative-tier hit disagrees with a
> `working_reference` one, the authoritative hit wins.*

`party.md` is generated by `pipelines/grounding/party.py`. The sheet is a D&D
Beyond export. The rule exists; it is simply not applied to the party roster.

### 3. One gap: subclass

Subclass is the only roster field the sheet's `## Identity` block does not
carry. It *is* on the sheet — but in D&D Beyond's own passthrough layout, which
renders differently per character:

- `zalthir.md:123` — `**Monk Subclass (PHB-2024 103) — Warrior of Shadow**`
- `soma.md:132–133` — `**Druid Subclass** • PHB-2024 81` / `| Circle of the Moon`

Not reliably parseable from the body. But it does not need to be: the fix is one
line in `dnd_sheet.py`'s prompt, where the format *is* controlled.

Minor, related: sheet player names are the D&D Beyond values and are sometimes
shorter than `party.md`'s (`Wade` vs `Wade Brown`), and `zalthir.md:5` has a
trailing space after `Gabe`. Under the ruling the sheet's values are correct;
the reader must `.strip()`.

## Approach

### 1. Extend the `## Identity` template

`pipelines/content_ingest/dnd_sheet.py`, `SYSTEM_PROMPT`: add `- **Subclass:**`
to the `## Identity` block. One line. This prompt is the only place the roster's
field set is defined, so it is the only place that needs to change.

### 2. Emit YAML frontmatter from `dnd_sheet.py`

Machine channel above, human channel below, same file, one GM review:

```yaml
---
name: Zalthir
player: Gabe
species: Dragonborn (Brass Dragon)
class_level: Monk 8
subclass: Warrior of Shadow
---
# Zalthir

## Identity
- **Class & Level:** Monk 8
...
```

Read with `campaignlib.textproc.split_frontmatter` — already canonical, 21
callers, real YAML. No new file format, no new parser.

`class_level` stays one string rather than decomposed class/level/subclass:
every consumer wants the rendered phrase, and splitting invents precision the
source lacks (`Human Fighter 9 / Bard 2` is a real value in Hillsfar's roster).

### 3. `PartyCharacter` is unchanged

`campaignlib/party_config.py` already carries `sheet:` per character. That
reference is the entire mechanism. Explicitly **not** adding `species` /
`class_level` — that was the superseded draft's move.

### 4. Serve the roster from the sheets

- `session_doc/roster.py` → `roster_from_config(cfg) -> str`
- `campaignlib/npc.py` → `player_map_from_config(cfg) -> dict[str, str]`

For each character: read `sheet:`, `split_frontmatter`, format. One parser, one
format.

Call sites — `sd_narrate.py:199`, `pipelines/ensemble/polish.py:842`,
`scene_extract.py:390` — prefer this, falling back to `party.md` until migration
completes. Per the standing no-back-compat rule the fallback is a **migration
ramp, not a permanent dual path**; it is deleted in step 6.

### 5. Migration: deterministic, zero-token, GM-gated

Existing sheets have no frontmatter, but their `## Identity` block is one
reliable format. A `sheet_frontmatter` importer parses it, proposes frontmatter,
the GM reviews, `--apply` writes. No API call, no re-extraction, PDFs not
required.

Subclass cannot be recovered from existing sheet bodies (fact 3), so the
importer leaves it blank and reports which characters need it. The GM fills it
in, or re-runs `dnd_sheet` with the updated prompt where the PDF is still to
hand.

**Conflicts are the point of the gate.** Where proposed frontmatter disagrees
with what `party.md` currently yields — Brass vs Bronze — the importer shows both
and the GM rules. **Do not auto-resolve, even toward the authoritative source:**
a mismatch may mean the sheet is stale (someone levelled up on paper and has not
re-exported) rather than `party.md` wrong. Which source is right in a given
conflict is a scope decision, and scope decisions get a human.

This follows the established shape — `dossier_proposer` writes a proposal the GM
approves before render pipelines consume it; `registry triage-candidates` walks
rulings one at a time. Template: `server/migrate_session_doc.py`, including its
refuse-to-clobber-without-`--force` convention and its "report unrecognised keys
rather than drop them" behaviour.

### 6. Demote the six-layout parser

`_parse_class_line` / `_parse_labeled_fields` / `_parse_oota_heading` /
`_strip_list_prefix` and their regexes move out of `session_doc/roster.py` into
the importer, where they serve as the `party.md` cross-check input. Delete the
step-4 fallback. `roster.py` keeps only `roster_from_config`.

`pipelines/grounding/party.py` keeps generating `party.md`. Its real value is
the narrative content — personality, relationships, items of significance, party
dynamics — not the stat line. It stays a document a human reads, and stops being
one the code reads back.


## Verification

1. `python -m pytest tests/` — existing `tests/test_roster.py` cases pass
   unchanged.
2. **The gate.** For all six campaigns, diff `roster_from_config(...)` against
   `extract_character_roster(party_md)`. Differences are **expected** here —
   Brass/Bronze is one — so the test asserts the diff matches a checked-in
   expected-conflicts file, with a GM ruling recorded per entry. (An earlier
   draft demanded byte-identical output; that was wrong, because the current
   output is wrong.)
3. Same comparison for `player_map_from_config` vs
   `extract_player_character_map`. Note this one currently returns `{}` for
   Phandalin, Hillsfar and out-of-the-abyss, so the new implementation should
   *gain* entries — filed separately at `priority:high`.
4. `sheet_frontmatter` twice without `--apply` → identical proposal, no mutation.
5. `sheet_frontmatter` on a sheet with no `## Identity` → clean refusal, no write.
6. `sd_narrate` before/after on a real session, diffing the assembled prompt —
   changes confined to lines the conflicts file explains.
7. `pytest tests/test_layering.py tests/test_retrieve_render_isolation.py` — the
   importer parses and proposes; it must make no API call.

## Relationship to #248

#248 reports that `extract_character_roster` "parses empty for Hillsfar /
obelisk / out-of-the-abyss / stormgiants / toee".

**That symptom is stale.** Verified 2026-08-10 by running the parser against all
six real `party.md` files: every campaign yields a non-empty roster. #246 and
subsequent work closed it.

Its proposed fix — "extend `roster.py` with one branch per catalogued layout" —
is superseded by this design, which removes the need for any branch. #248 still
carries useful #245/#246 lineage, so whether to close it is the GM's call.
