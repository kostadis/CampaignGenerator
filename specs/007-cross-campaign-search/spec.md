# Feature Specification: Cross-Campaign Provenance-Aware Search Seam

**Feature Branch**: `007-cross-campaign-search`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: a read-only, cross-campaign search capability over the six-campaign workspace at `~/src/campaigns`, exposed to Claude Code sessions as an MCP server. The problem is not recall — grep already finds every string in the corpus in under a second. The problem is **provenance**: hits arrive as bare text with nothing attached saying which trust tier they came from, whether the file is machine-generated and therefore stale, which campaign owns them, or as of which chapter they were true.

## Problem Statement

Search results in this workspace are **unlabeled**. A line pulled from a machine-generated grounding doc that will be clobbered on the next pipeline run is visually indistinguishable from a line in a hand-written session summary that is canon. The GM — or a Claude session acting for the GM — then treats the stale generated line as fact, and the error propagates into session prep, consistency checks, and eventually to the table.

The workspace `CLAUDE.md` already defines a trust hierarchy: **Authoritative** (session summaries, VTTs, chapter splits) / **Search accelerator** (`distill_extractions/`, `planning_extractions/`) / **Working reference** (generated grounding docs, NPC dossiers), plus a fourth implicit tier, **Staging** (`notes/`, deliberately excluded from semantic mining because it is unreviewed). That hierarchy exists **only in prose**. No tool emits it and no script can read it. The known corrections to specific stale files live only in a Claude memory directory outside the repo, invisible to every tool the GM runs.

### Documented incidents — the failure is provenance, not recall

In each case the correct string was retrievable; the retrieval was still wrong because the source's tier was invisible.

| # | Campaign | Incident |
|---|---|---|
| 1 | Phandalin | `docs/world_state.md` (generated by `distill.py`, never hand-editable) states the Woodland Manse is "Active; Grannoc performing ritual; NOT visited." The Manse has been **empty since Chapter 43**. A consistency check trusting `world_state.md` false-positived a correct recap as a continuity error. |
| 2 | toee | `docs/npcs/calmer.md` records Calmer as "Dead, killed by Thalsor." Calmer is a **living PC** operating undercover as Supreme Prophet of the Upper Temple. |
| 3 | toee | `docs/party.md` has Sequioa's and Zephyr's species swapped, attributing fire resistance to the wrong PC in a statblock note. |
| 4 | obelisk | The authoritative naming source is the hand-curated `docs/background/name_glossary.md` plus `characters/*.md`, but `check_consistency.py` loads only the generated `world_state`/`campaign_state` — so it false-flags canon surnames (Dawnforge) as unattested and misses errors the generated docs share (Forepot for Foreput). |
| 5 | multiple | Query-time alias failures: "Vera" should reach Veyra; "KP" must **not** reach "Kostadinious the Sage" (an in-world biographer, a recurring LLM misidentification); "Unla" and "Key" are one halfling PC, not two characters. |

### Measured current state (verified 2026-08-04, host Linux-Alien)

- 6 campaigns under `~/src/campaigns`: Phandalin, out-of-the-abyss, stormgiants, toee, Hillsfar, obelisk. **9,273 markdown files, 408 MB.**
- 244 chapter files, 676 NPC dossiers, 72 VTT transcripts, ~174 notes files.
- The existing `campaign` and `registry` MCP servers are each **pinned to a single campaign at process start** (`--campaign-dir` / `CAMPAIGN_DIR`, currently `out-of-the-abyss`). Searching a different campaign requires editing `.mcp.json` and restarting the session. **There is no cross-campaign front door.**
- The `5etools` MCP server is currently failing to connect (`-32000`).
- MemPalace is **not installed on this machine** (`~/.mempalace/palaces/` is empty), so every semantic-search path silently degrades to "no results" — indistinguishable from a genuine miss. It *is* installed on the WSL2 desktop (`SiliconValley`). Availability is per-machine and currently invisible to the caller.
- Human-curated identity stores exist for **4 of 6** campaigns (`docs/entity_registry.yaml`, 82–126 KB each, plus `docs/aliases.json`). **stormgiants and Hillsfar have neither.**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Where does this fact actually come from? (Priority: P1)

The GM, or a Claude session acting for the GM, searches one explicitly named campaign for a subject. Every hit comes back wrapped in a provenance envelope: which campaign owns it, its repo-relative path, its trust tier, whether it is machine-generated and by which pipeline stage, the chapter or date it reflects, and any recorded known-stale correction — attached inline, next to the excerpt. Results are ordered by relevance with **trust tier as a tiebreak**, so an authoritative source outranks a generated one at equal relevance.

**Why this priority**: This alone prevents the entire documented failure class. Incidents 1, 2 and 4 all reduce to "a generated file was read as canon." Labeling every hit removes that possibility without any other capability existing. It is a viable MVP on its own.

**Independent Test**: Search Phandalin for "Woodland Manse". Confirm the `docs/world_state.md` hit returns tagged `working-reference` / `generated-by: distill.py` / `known-stale`, with the recorded correction ("empty since Chapter 43") attached, and that the authoritative chapter-43 material is also returned and ranks above it at equal relevance.

**Acceptance Scenarios**:

1. **Given** the Phandalin manifest classifies `docs/world_state.md` as working-reference generated by `distill.py`, and the Phandalin corrections record contains the Woodland Manse entry, **When** the GM searches Phandalin for "Woodland Manse", **Then** the `world_state.md` hit carries tier, generated-by stage, and the correction text inline, and the authoritative chapter-43 hit is ranked above it at equal relevance.
2. **Given** a search that matches files across several tiers, **When** results are returned, **Then** every hit carries a complete provenance envelope and no hit is returned as bare text.
3. **Given** a caller applies a tier filter that excludes some matching hits, **When** results are returned, **Then** the response reports the count of suppressed hits and which tiers they were in — never a silently shortened list.
4. **Given** a search request that names no campaign and does not explicitly request cross-campaign scope, **When** the request is made, **Then** it is refused with an explicit message naming the missing scope, and no results are returned.
5. **Given** a campaign has no manifest entry, **When** it is searched, **Then** the request is refused with an explicit message naming the missing manifest — never served with hits labeled as an unknown or guessed tier.

---

### User Story 2 - Which name is this, really? (Priority: P2)

Given a surface form and a campaign, the GM gets back the canonical entity, its known aliases, known-wrong variants, and — critically — recorded **known confusions**: pairs that look alike but are distinct entities. Search can then expand a query across aliases so misspelled variants still hit. Name similarity is never presented as evidence of identity.

**Why this priority**: Incident 5 is a recurring, self-reinforcing error — an LLM that once conflated "KP" with "Kostadinious the Sage" will do it again every session. Alias expansion also raises the recall of Story 1 without changing its contract. It depends on Story 1's envelope but is separately demonstrable.

**Independent Test**: Resolve "Vera" in obelisk → returns Veyra. Resolve "KP" in Phandalin → returns Kazneporium Ketternopappux **with an explicit non-identity note for Kostadinious the Sage**. Resolve any name in stormgiants → returns "no identity store for this campaign," not a guess and not an empty result.

**Acceptance Scenarios**:

1. **Given** obelisk has an identity store recording Veyra with alias "Vera", **When** the GM resolves "Vera" in obelisk, **Then** the canonical form Veyra is returned with its alias set.
2. **Given** Phandalin's identity store records a known confusion between "KP"/Kazneporium Ketternopappux and Kostadinious the Sage, **When** the GM resolves "KP" in Phandalin, **Then** Kazneporium Ketternopappux is returned **and** the response carries an explicit statement that Kostadinious the Sage is a distinct entity.
3. **Given** stormgiants has neither `docs/entity_registry.yaml` nor `docs/aliases.json`, **When** the GM resolves any name in stormgiants, **Then** the response states "no identity store for this campaign" — an answer distinguishable from both a miss and a match.
4. **Given** a surface form that resembles a known entity but has no recorded alias link, **When** it is resolved, **Then** the response does not claim identity on the basis of string similarity.
5. **Given** a resolved entity with aliases, **When** a search is run with alias expansion enabled, **Then** hits matching any alias are returned and each records which surface form matched.

---

### User Story 3 - Can I trust this empty result? (Priority: P3)

Before relying on a "no hits" answer, the caller can ask which campaigns exist and which retrieval backends are actually live **on the current machine**. A backend that is not installed is reported as unavailable, never as zero hits.

**Why this priority**: MemPalace is absent on this host and present on the WSL2 desktop, so the same query silently means different things on different machines. This is Principle VIII (State is Discoverable) made operational, and it is cheap. It is lower than P1/P2 only because the first increment ships one always-available backend, which bounds the immediate damage.

**Independent Test**: On this host, ask for capabilities. Confirm the response enumerates all six campaigns with their manifest/identity-store/corrections status, and reports the semantic backend as **unavailable — not installed on this machine**, distinct from "available, returned nothing."

**Acceptance Scenarios**:

1. **Given** MemPalace is not installed on the current host, **When** the caller requests capabilities, **Then** the semantic backend is reported unavailable with a reason, and is never reported as returning zero results.
2. **Given** the caller requests capabilities, **When** the response is returned, **Then** each of the six campaigns is listed with whether it has a manifest entry, an identity store, and a corrections record.
3. **Given** a backend is unavailable, **When** a search runs that would have consulted it, **Then** the search response records that the backend did not contribute — the result set is never presented as complete.

---

### User Story 4 - What did the world look like at chapter N? (Priority: P4)

Campaigns are released chapter by chapter with a recorded horizon marker. The GM can ask what was true as of chapter N, filtering out material from later chapters. Within a campaign, provenance ranges are distinguished: in out-of-the-abyss, chapters 1–15 are hand-written by the GM and 16+ are AI-assisted — not interchangeable for voice-reference work even though both are canon for plot.

**Why this priority**: Real but narrower than P1–P3. It matters most when preparing a recap or checking a claim against what was knowable at the time, and it depends on horizon data the manifest already has to carry for Story 1.

**Independent Test**: Search out-of-the-abyss with a horizon of chapter 15 and confirm no chapter-16+ material is returned; run the same search with no horizon and confirm the later material appears, tagged as the AI-assisted provenance range.

**Acceptance Scenarios**:

1. **Given** out-of-the-abyss records chapters 1–15 as GM-written and 16+ as AI-assisted, **When** a search returns hits from both ranges, **Then** each hit's envelope names its provenance range.
2. **Given** a horizon of chapter N, **When** a search runs, **Then** no material attributed to a chapter later than N is returned, and the count of hits excluded by the horizon is reported.
3. **Given** a file the manifest cannot attribute to a chapter, **When** a horizon filter is applied, **Then** the file's disposition is explicit in the response rather than silently dropped.

---

### User Story 5 - Deliberate cross-campaign search (Priority: P5)

There is one legitimate cross-campaign query class: prior-campaign PCs who are now canonical historical figures in a later campaign. The GM can search across campaigns, but only by explicitly asking for it. Cross-campaign is never the scope the system falls into when no campaign was named.

**Why this priority**: A real need, but rare, and it is the highest-risk surface in the feature — bleeding one game's state into another is a known failure. It ships last so the single-campaign boundary is proven first.

**Independent Test**: Issue a search with explicit multi-campaign scope and confirm hits from each named campaign are returned, each labeled with its owning campaign; then issue the same search with no scope and confirm it is refused rather than defaulting to all six.

**Acceptance Scenarios**:

1. **Given** a caller explicitly names two campaigns, **When** the search runs, **Then** hits from both are returned, each labeled with its owning campaign.
2. **Given** a caller omits scope entirely, **When** the search runs, **Then** it is refused — the system never materializes "all campaigns" on the caller's behalf.
3. **Given** a cross-campaign search, **When** results are returned, **Then** hits are never merged or de-duplicated across campaigns in a way that obscures which game each came from.

---

### Edge Cases

- **Manifest missing for a campaign** → refuse that campaign's queries with an explicit message. Never serve hits with a guessed or defaulted tier.
- **Manifest present but a matched file matches no tier glob** → the file is reported as unclassified and its hit is labeled unclassified, not silently assigned a tier and not silently dropped.
- **Corrections record missing or empty** → search still works; the envelope's correction field is explicitly empty rather than absent, so "no correction recorded" is distinguishable from "corrections not consulted."
- **A correction references a file that no longer exists** → reported as a stale correction entry so the GM can prune it; it does not crash the query.
- **Tier filter excludes every hit** → the response is an explicit "all N hits suppressed by filter," not an empty result set.
- **Identity store present but the surface form is genuinely unknown** → "not found in identity store," distinct from "no identity store for this campaign."
- **Two campaigns contain an entity with the same name** → cross-campaign results keep them separate and never assert they are the same entity.
- **A file is both machine-generated and hand-edited afterward** → the manifest's declaration governs; the file is labeled generated, because the next pipeline run will clobber the hand edits. This is a warning condition worth surfacing.
- **Horizon requested for a campaign with no recorded horizon marker** → refuse the horizon filter explicitly rather than returning unfiltered results as if filtered.
- **Corpus grows past the point where exhaustive scanning is fast** → a degraded-latency condition the caller can observe, not a silent truncation of results.

## Requirements *(mandatory)*

### Functional Requirements

**Provenance envelope**

- **FR-001**: System MUST return every search hit wrapped in a provenance envelope. No hit is ever returned as bare text.
- **FR-002**: Each envelope MUST carry, at minimum: owning campaign; repo-relative path; trust tier; machine-generated status and the generating pipeline stage; the chapter or date the content reflects; any recorded known-stale correction for that file or subject; and the excerpt.
- **FR-003**: System MUST express machine-generated status such that a non-null generating stage means "will be clobbered on regeneration, may be stale."
- **FR-004**: System MUST attach a recorded correction inline with the hit it applies to, not in a separate section the caller may not read.
- **FR-005**: System MUST distinguish "no correction is recorded" from "corrections were not consulted."

**Scope**

- **FR-006**: System MUST require an explicit scope on every search. A request naming no campaign MUST be refused with a message naming the missing scope.
- **FR-007**: System MUST support cross-campaign search only as a deliberate, explicitly requested act.
- **FR-008**: System MUST label every hit with its owning campaign, including in cross-campaign results, and MUST NOT merge entities across campaigns.
- **FR-009**: System MUST refuse queries against a campaign that has no manifest entry, rather than serving hits with a defaulted tier.

**Ranking and suppression**

- **FR-010**: System MUST order results by relevance using trust tier as a tiebreak, so an authoritative source outranks a generated one at equal relevance.
- **FR-011**: System MUST report the count and tiers of any hits suppressed by a tier filter. Suppressed results are never silently omitted.
- **FR-012**: System MUST report hits excluded by a chapter-horizon filter as a count, not silently drop them.
- **FR-013**: System MUST label a matched file that fits no tier glob as unclassified rather than assigning it a tier.

**Identity resolution**

- **FR-014**: System MUST resolve a surface form within a named campaign to its canonical entity, aliases, and known-wrong variants, reading the existing identity stores without modifying them.
- **FR-015**: System MUST return recorded known confusions — pairs that look alike but are distinct entities — as part of a resolution.
- **FR-016**: System MUST NOT present name similarity as evidence of identity.
- **FR-017**: System MUST return an explicit "no identity store for this campaign" for campaigns lacking one, distinguishable from both a match and a miss.
- **FR-018**: System MUST distinguish "not found in this campaign's identity store" from "this campaign has no identity store."
- **FR-019**: System MUST support expanding a search across a resolved entity's aliases, recording which surface form produced each hit.

**Capability discovery**

- **FR-020**: System MUST report which retrieval backends are live on the current machine before the caller has to trust an empty result.
- **FR-021**: System MUST report an uninstalled backend as unavailable with a reason, never as zero hits.
- **FR-022**: System MUST record in each search response which backends contributed, so a result set is never implied to be complete when a backend was absent.
- **FR-023**: System MUST enumerate the campaigns it knows about, each with whether it has a manifest entry, an identity store, and a corrections record.

**Horizon and provenance ranges**

- **FR-024**: System MUST support filtering results to what was true as of a given chapter, where the campaign records a horizon marker.
- **FR-025**: System MUST refuse a horizon filter for a campaign with no recorded horizon marker rather than returning unfiltered results as if filtered.
- **FR-026**: System MUST label each hit with its within-campaign provenance range where the manifest declares ranges.

**Authored data (in scope as deliverables)**

- **FR-027**: A workspace-level manifest MUST exist at `~/src/campaigns/`, declaring per campaign: tier path globs; which files are pipeline-generated and by which stage; the horizon marker; identity-store paths; the path to that campaign's corrections record; and any within-campaign provenance ranges.
- **FR-028**: A per-campaign corrections record MUST exist at `<campaign>/docs/corrections.yaml`, seeded with the five documented incidents above, and MUST live in the repo as truth on disk.
- **FR-029**: Both the manifest and the corrections records MUST be hand-authored. Nothing may populate them by inference.
- **FR-030**: System MUST fail loudly on a malformed manifest or corrections record rather than proceeding with partial data.

**Read-only guarantees**

- **FR-031**: System MUST NOT write to campaign content under any circumstances.
- **FR-032**: System MUST NOT mutate identity data. Aliasing, merging, marking-distinct and marking-rejected remain with the existing registry tooling behind explicit human confirmation.
- **FR-033**: System MUST NOT make an LLM call anywhere in the capability. Ranking and labeling are deterministic.

### Key Entities

- **Campaign**: One game, one directory under `~/src/campaigns`, with its own state and its own commit history. The hard boundary of the feature.
- **Provenance Manifest**: The workspace-level, hand-authored declaration mapping each campaign's path globs to trust tiers, generating stages, horizon marker, identity-store paths, corrections-record path, and provenance ranges. The only thing that converts prose policy into machine-readable labels.
- **Trust Tier**: One of Authoritative / Search accelerator / Working reference / Staging, plus an explicit *unclassified* state for files no glob covers.
- **Provenance Envelope**: The label set attached to every hit. Its completeness is the feature's core guarantee.
- **Correction Record**: A per-campaign, hand-authored entry recording that a specific file or subject is known stale, with what the truth is and as of when. Seeded from the five documented incidents.
- **Identity Store**: An existing, human-curated per-campaign registry (`docs/entity_registry.yaml`, `docs/aliases.json`). Read-only input; present for 4 of 6 campaigns.
- **Known Confusion**: A recorded assertion that two similar-looking names are **distinct** entities. Carries the same weight as an alias and prevents a recurring class of LLM error.
- **Chapter Horizon**: The marker recording how far a campaign has been released, enabling "as of chapter N" filtering.
- **Provenance Range**: A within-campaign span distinguishing authorship mode (e.g. out-of-the-abyss chapters 1–15 GM-written, 16+ AI-assisted).
- **Backend**: A retrieval mechanism whose availability is per-machine and must be reported honestly.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of returned hits carry a complete provenance envelope. A sweep across all six campaigns produces zero hits with a missing required field.
- **SC-002**: All five documented incidents are reproduced as test cases, and in each the misleading source is labeled such that a reviewer identifies it as stale **without opening the file**. Target: 5 of 5.
- **SC-003**: A search naming no scope returns zero results and an explicit refusal 100% of the time. There is no input that causes the system to search all campaigns implicitly.
- **SC-004**: When a backend is unavailable, the response distinguishes "unavailable" from "zero hits" in 100% of cases.
- **SC-005**: 100% of hits suppressed by tier or horizon filtering are reported with a count. Zero silent omissions.
- **SC-006**: For campaigns without an identity store, resolution returns the explicit no-store answer 100% of the time and never a guessed canonical form.
- **SC-007**: A single-campaign search over the 9,273-file corpus returns fast enough that the GM stays in flow — under 2 seconds at the 95th percentile.
- **SC-008**: The GM can determine which trust tier any hit came from in a single read, without consulting `CLAUDE.md` or any other document.
- **SC-009**: Deleting every derived artifact the feature produces and rebuilding it from disk yields identical results, confirming disk remains the only truth.
- **SC-010**: Zero writes to campaign content occur during any operation, verified by comparing the workspace's state before and after a full exercise of every operation.

## Constitution Alignment

Checked by name, as required.

- **I — Disk is Truth, the Model is a Draft.** The manifest and corrections records are hand-authored markdown/YAML on disk. The first increment introduces no index at all; any future index is a cache over disk, deletable and rebuildable, and disk is never rebuilt from it (SC-009). Machine-generated files are labeled precisely so a *draft* is never mistaken for canon — this feature is Principle I made legible at query time.
- **II — The Human Checkpoint is Non-Negotiable.** **What decision does this remove from the human? None.** The capability labels and retrieves; it does not decide. It contains no LLM call (FR-033), so there is no precision boundary to cross. The one place a scope decision could leak in is **tier filtering that silently drops hits** — a renderer quietly deciding what is in the world. FR-011, FR-012 and SC-005 close it: suppressed results are always reported and counted, never quietly omitted.
- **III — Retrieval and Render are Separated.** This is a pure retrieval seam with no render path. It satisfies `tests/test_retrieve_render_isolation.py` trivially, because no function in it calls `stream_api` or `call_api` at all.
- **IV — Verbatim is Sacred.** Excerpts are reproduced exactly from disk and never paraphrased, summarized, or "improved." No LLM touches them.
- **V — One Seam per Boundary.** The constitution names `mcp_server.py` as the seam for "CampaignGenerator capability exposed outward to other Claude sessions." **GM ruling: a new unpinned sibling MCP server**, read-only, with campaign scope passed per call. The burden this creates is argued explicitly rather than assumed: *read-only retrieval across campaigns* is a different boundary from *operating on one campaign*. The existing `campaign` server's write and pipeline-invocation tools legitimately want a pinned campaign — unpinning them would give every write a scope argument, so a mis-scoped write could silently land in the wrong game. A read-only process also makes Principle X trivially enforceable, because there is nothing to clobber. **Rejected**: unpinning the existing `campaign` server; extending the RLM `pipelines/rlm/mcp_server.py`, whose boundary is RPG *library* canon — a different corpus with a different trust model.
- **VIII — State is Discoverable.** Per-machine backend availability and per-campaign data completeness are reported by the tool (FR-020 – FR-023), not held as tribal knowledge about which host has MemPalace installed.
- **X — Selection is Explicit; There is No Silent "All".** Scope is required on every query (FR-006). Cross-campaign is a deliberate act (FR-007). There is no input that causes the system to fall into searching everything (SC-003).

## Out of Scope

- **No new corpus index and no daemon in the first increment.** 408 MB of markdown is trivially greppable. A semantic index is a cache over disk truth, subject to drift, and must justify its standing cost. Semantic retrieval is a later, optional backend.
- **No writes of any kind to campaign content.** This capability retrieves and labels.
- **No identity mutation.** Aliasing, merging, marking-distinct and marking-rejected stay with the existing registry tooling behind explicit human confirmation.
- **No LLM call anywhere in the capability.** Ranking and labeling are deterministic.
- **Not a replacement** for the existing per-campaign `campaign` MCP server's write and pipeline-invocation surface. This is retrieval only.
- **No bootstrapping of identity stores for stormgiants and Hillsfar.** Per GM ruling, identity resolution degrades honestly for those two. Building a registry belongs to the existing tooling (the `gm-module-inventory` skill feeding `registry import-inventory`), a human-checkpoint-heavy flow that would put a scope-decision pipeline inside a pure retrieval spec.

## Deferred to a Later Increment

**Typed claim verification** — "Is this claim actually supported?" Verify a typed claim against its correct authoritative source rather than its source of assertion, using a route table:

| Claim type | Authoritative source (not the source of assertion) |
|---|---|
| "PC X cast spell Y" | `characters/*.md` — the character sheets |
| "NPC X is alive/dead" | Authoritative chapter material, not NPC dossiers |
| "Location X is occupied by Y" | Authoritative chapter material, not `world_state.md` |

A sheet miss is a **question for the GM, not a verdict** — bards can hold spells outside their class list via Magical Secrets, so "not on the sheet" does not mean "did not happen."

**Cost of the deferral, stated plainly**: incidents 2 and 3 — Calmer recorded dead, and the Sequioa/Zephyr species swap — are exactly this shape. Labeling those sources as generated and known-stale (Story 1) mitigates them; it does not catch a *new* instance of the same error before someone records a correction. That gap stays open until this increment lands.

## Assumptions

- **Increment 1 = Stories 1 and 2** (provenance-labeled scoped search + identity resolution), per GM ruling. Stories 3–5 are in scope for the feature and prioritized below them.
- **The manifest is a single workspace-level file** at `~/src/campaigns/`, because it is the one file that must answer "which campaigns exist" (FR-023) without a guessing scan. The six campaigns share one git repo; corrections stay per-campaign because that repo's `CLAUDE.md` forbids cross-campaign commits. Its exact filename is a planning-phase decision.
- **Corrections live per campaign, inside the campaign**, at `<campaign>/docs/corrections.yaml`. A correction is campaign truth and versions with the game that owns it; a campaign stays self-describing if moved or cloned alone. **Rejected**: one shared workspace-wide file (not versioned with what it describes; a merge point across six independent games) and a per-campaign-file-stored-centrally hybrid (splits a campaign's truth across two locations — a Split-Brain shape).
- **Missing or malformed manifest data is a refusal, not a degradation.** Serving a hit with a guessed tier would reintroduce the exact failure the feature exists to prevent. Missing *identity* data degrades honestly instead, because "no identity store" is a complete and useful answer where "unknown tier" is not.
- **The four trust tiers are taken as given** from the workspace `CLAUDE.md`, including Staging (`notes/`) as a real fourth tier rather than an oversight. This feature transcribes that hierarchy into machine-readable form; it does not redesign it.
- **Existing identity stores are read as-is.** Their schema is an input constraint, not something this feature changes.
- **Chapter attribution comes from the manifest**, not from parsing file contents — inferring it would violate FR-029.
- **The five documented incidents are the seed corpus** for the corrections records and double as the feature's acceptance fixtures.
- **The workspace at `~/src/campaigns` is separate from this repository.** Code ships here; the manifest and corrections data live there. How the seam locates the workspace root is a planning-phase decision, subject to Principle VIII (it must be discoverable, not tribal).
- **The `5etools` MCP server's `-32000` failure is out of scope** — noted as current-state context, not a problem this feature fixes.
